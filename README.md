# See who is working on each order

```
```sh
npm install
INFRAI_API_KEY=your_key npm run dev
```
```

We run this service to surface two signals for the ops workspace: live presence and recent order state changes. Infrai delivers both via one API and a single `INFRAI_API_KEY`; we keep that credential server-side and hand out short-lived client tokens. That boundary matters because a leaked key means replayed transitions and paged incidents.

## Send a checkout transition

Open another terminal to fire the transition:

```
```sh
npm run demo
```
```

The script posts the domain payload to the local service:

```
```json
{
  "requestId": "a UUID generated by the script",
  "accountId": "shop-demo",
  "update": {
    "kind": "checkout_started",
    "orderId": "ord_1042",
    "customerId": "cus_71"
  }
}
```
```

You should see:

```
```json
{"accepted":true,"event":"checkout.started","orderId":"ord_1042"}
```
```

The same request boundary accepts `fulfillment_started`, `receipt_issued`, and `customer_updated`. We validate each with zod, map to a workspace event, and publish it to `commerce-ops`. `requestId` becomes the idempotency key. If a job retries after a timeout, the write still results in exactly one transition. Missed jobs are bad; duplicate deliveries are worse.

## Read presence and issue browser access

Browser clients request a scoped token from this service. The root key stays server-side; it never crosses to the client.

```
```sh
curl -sS -X POST http://localhost:8787/session \
  -H 'content-type: application/json' \
  -d '{"clientId":"operator-17"}'

curl -sS -X GET http://localhost:8787/online
```
```

`GET /online` returns the current presence data for the workspace channel. We create that channel at startup as part of the runbook. Every Infrai request sets its HTTP method, decodes the response envelope before interpreting status, surfaces business rejections with their client status, and backs off on HTTP 429 while honoring `Retry-After`. In Go you'd wrap this with a retry that honors the Retry-After header.

## Verify the decision

```
```sh
npm test
npm run typecheck
```
```

The focused test supplies `receipt_issued` for `ord_1042` and expects `receipt.issued` with the matching receipt ID. It also checks that a customer update without `message` is rejected at the zod boundary before any publish. We learned the hard way that missing idempotency fields cause double-sends.

The example stops at the service boundary. A workspace UI can take the returned token, open its realtime connection, and show presence next to the order feed.
